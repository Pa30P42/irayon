# Этап 2 — чек-лист ручного QA

Бронирования: заявка → принятие/отклонение → отмена, доступность, календарь хоста, крон.

## Что уже проверено, а что нет

Проверено на реальной базе и по HTTP: инвариант конкурентности (два одновременных
принятия, три раунда, ровно один победитель в каждом — и победитель менялся),
слепок цены переживает изменение цены посреди заявки, бронирование самому себе и
дубликаты заявок отклоняются, прошедшие даты отклоняются по бакинскому времени,
блокировки, пересекающиеся с принятыми бронированиями, отклоняются, крон
просрочивает только то, что должен.

**Не проверено: браузер.** Виджет календаря, две конвертации полуоткрытых
интервалов дат вокруг него и то, как всё это выглядит на телефоне.

## Подготовка

```bash
pnpm dev
```

Учётные записи те же, что на этапе 1. Нужны **два** браузера (или один плюс
приватное окно) — самое интересное требует гостя и хоста одновременно:

| Email                  | Роль                                            |
| ---------------------- | ----------------------------------------------- |
| `guest@example.com`    | гость, отправляющий заявки                      |
| `testhost@example.com` | хост, получающий их (владеет `test-host-cabin`) |

Держите терминал с `pnpm dev` на виду — каждое письмо печатается там строкой
`email_logged`.

---

## A. Гость — отправка заявки

На `/az/listings/test-host-cabin`, без входа:

- [ ] Карточка бронирования показывает цену и кнопку **Войдите, чтобы забронировать**
- [ ] Клик ведёт на страницу входа, и после входа вы возвращаетесь **на это
      объявление**, а не на главную

Теперь под `guest@example.com`:

- [ ] Откройте выбор дат — прошедшие даты неактивны
- [ ] Выберите диапазон → появляются количество гостей, поле заметки и разбивка цены
- [ ] Разбивка сходится: ночи × цена + плата за уборку. Если плата равна 0, строка
      скрыта целиком, а не показывает «0»
- [ ] Строка под кнопкой говорит, что это не мгновенное бронирование
- [ ] Отправьте заявку → карточка заменяется подтверждением со ссылкой на ваши
      бронирования
- [ ] В терминале есть строка `email_logged` с `booking-update` для **хоста**

Негативные сценарии:

- [ ] Запросите те же даты ещё раз → _«У вас уже есть заявка в ожидании»_
- [ ] Войдите как `testhost@example.com` и попробуйте забронировать **своё
      собственное** объявление → отказ, на азербайджанском, а не сырым английским

## B. Гость — управление бронированиями

`/az/account/bookings`:

- [ ] Ваша заявка есть в списке с датами, количеством ночей, гостей, статусом
      **В ожидании** и итоговой суммой
- [ ] У заявок в ожидании показан срок «ответить до»
- [ ] Отмена → диалог подтверждения → строка становится **Отменено**
- [ ] После отмены кнопка «Отменить» исчезает

`/az/account/settings`:

- [ ] Имя, телефон и язык уведомлений сохраняются и переживают перезагрузку
- [ ] **Email неактивен и не редактируется**
- [ ] Поставьте язык «русский», затем попросите хоста принять бронирование → письмо
      в терминале приходит на русском

## C. Хост — входящие

Под `testhost@example.com` на `/az/host/bookings`:

- [ ] Работают четыре вкладки: В ожидании / Предстоящие / Прошедшие / Все
- [ ] Заявка в ожидании показывает имя гостя, написанную им заметку и срок
      **ответить до**
- [ ] Итог подписан как **«цена на момент заявки»**
- [ ] **Принять** → заявка переезжает из «В ожидании» в «Предстоящие»
- [ ] В терминале есть письмо `booking-update` для **гостя**
- [ ] На `/az/account/bookings` у гостя теперь **Подтверждено**
- [ ] Бейдж в шапке в окне гостя показывает счётчик непрочитанного

Отклонение и отмена:

- [ ] Создайте вторую заявку, затем **Отклоните** её с причиной → гость видит
      причину на своей странице бронирований
- [ ] Примите третью, затем **Отмените** её как хост → диалог подтверждения, затем
      «Отменено»

**Тест на цену — тот самый, который стоит сделать внимательно:**

- [ ] При заявке в ожидании зайдите на `/az/host/listings/<id>/edit` и **поднимите
      цену**, сохраните
- [ ] Вернитесь на `/az/host/bookings` → заявка в ожидании по-прежнему показывает
      **исходный** итог, а не новый
- [ ] Примите её → и подтверждение, и страница гостя всё так же показывают исходный
- [ ] Сама страница объявления показывает новым посетителям новую цену

## D. Доступность

- [ ] При **принятом** бронировании откройте выбор дат на объявлении как гость →
      эти ночи неактивны
- [ ] **День выезда по-прежнему выбирается.** Если проживание с 5-го по 8-е, 8-е
      должно быть доступно — это день пересменки, а не занятая ночь. Самое вероятное
      место, где прячется ошибка на единицу
- [ ] Отмените бронирование → ночи снова становятся выбираемыми

## E. Календарь хоста

`/az/host/calendar`:

- [ ] Выпадающий список показывает ваши объявления; переключение сбрасывает выбор
- [ ] Выберите диапазон, добавьте заметку, **Заблокировать даты**
- [ ] Список показывает именно тот диапазон, который вы закрыли — заблокировав с
      20-го по 22-е, должно читаться **20 → 22**, а не 20 → 23
- [ ] Эти дни теперь неактивны в календаре выше
- [ ] Те же даты неактивны для гостей на публичной странице объявления
- [ ] **Разблокировать** → они возвращаются
- [ ] Попробуйте заблокировать даты, покрывающие **принятое** бронирование → отказ
      с текстом «на эти даты есть подтверждённое бронирование»

## F. Публичный профиль хоста

- [ ] `/az/hosts/<hostId>` открывается **без входа** и показывает имя хоста, год
      регистрации и его активные объявления
- [ ] Он **не** показывает email или телефон
- [ ] Выдуманный id отрисовывает страницу «не найдено»

## G. Крон

```bash
SECRET=$(grep '^CRON_SECRET=' .env.local | cut -d'"' -f2)
curl -s http://localhost:3000/api/cron/bookings                                  # 401
curl -s -H "Authorization: Bearer $SECRET" http://localhost:3000/api/cron/bookings
```

- [ ] Без токена: 401. С токеном: JSON-сводка
- [ ] В терминале есть строка `cron_bookings_done` со счётчиками

Чтобы увидеть, как он действительно что-то просрочивает, создайте заявку, сдвиньте
её `expiresAt` в прошлое через `pnpm prisma:studio` и запустите крон снова.

## H. Локализация и вёрстка

- [ ] Карточка бронирования, `/account/bookings`, `/host/bookings`,
      `/host/calendar` на всех трёх локалях — никаких сырых ключей вроде
      `host.bookings.title`
- [ ] Выбор дат при ~375px не вылезает за карточку
- [ ] Входящие хоста при ~375px — кнопки переносятся, а не растягивают страницу вбок

---

## Известное и ожидаемое

- **`/az/host/bookings` не для хоста возвращает HTTP 200**, а не 3xx. Редирект всё
  равно происходит — Next разрешает его на клиенте, потому что оболочка страницы уже
  отдана потоком. То же и с несуществующим профилем хоста: содержимое 404, статус 200.
- Сообщения, жалобы и `/admin/users` относятся к этапу 3 и отсутствуют.
- Письма идут в терминал, ограничение частоты — в памяти, вход — это dev-форма;
  все три подключаются в конце.

## Сброс

```bash
pnpm dev  # затем, в другом шелле:
```

Почистите тестовые бронирования/блокировки через `pnpm prisma:studio` или снесите
всё и начните заново: `pnpm prisma:reset && pnpm prisma:seed` (последовательность
«вход → бэкфилл», которая за этим следует, описана в документе этапа 1).
